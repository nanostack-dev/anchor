The replay middleware

It does one thing: it makes the write reach OpenFGA before the client gets its response.

The problem it solves

An admin adds Ana to Acme, then the browser loads Ana's page at once. OpenFGA only learns about Ana when somebody syncs the mark.

With the middleware

This is "read your own writes": once the client has its 201, every later check already agrees with Postgres. PR 7 needs this before checks can move from Postgres to OpenFGA.

Why a middleware, and not the service?

  • The sync must run after the commit. Desired reads Postgres from another connection. Before the commit it does not see Ana's row, so it would write nothing. The middleware wraps the handler, so when f returns, the commit is done.
  • One place for every write. Members, roles, API keys and the catalog all emit events. No service has to know about OpenFGA or call a sync.
  • The basket tells the middleware what to sync. Without it, the middleware would have to query authz_sync_marks and could pick up other requests' marks.

What if something goes wrong?

CaseResult
The handler returns an errorThe transaction rolled back, with its mark. No replay.
The replay fails (OpenFGA down, lock busy)A warning is logged and the client still gets its 201. The mark row stays in Postgres, so the sweeper retries it within 5 s.
The client disconnects during the replayThe replay uses context.WithoutCancel, so it finishes anyway.
A catalog change marks the whole ProductThe replay can be long. It stops after 30 s, and the sweeper finishes it.
A request that changes no accessThe basket is empty, so Replay returns at once. The cost is zero.
A background job writes (no HTTP request)No basket exists. The mark is still written, and the sweeper syncs it.
